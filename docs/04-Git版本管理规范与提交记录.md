## 一、提交信息规范（Conventional Commits 简化版）

格式：

```
<类型>: <一句话说明做了什么>

<可选：分条说明具体改动与原因>
```

| 类型 | 含义 | 本项目示例 |
| --- | --- | --- |
| `feat` | 新增功能 / 新板块 | `feat: 内容与结构改为求职导向，新增教育背景/课程/证书板块` |
| `style` | 只改样式，不改逻辑与内容含义 | `style: 视觉改为专业简洁风…` |
| `docs` | 只改文档 | `docs: 补全需求、设计、部署与测试文档` |
| `content` | 只改页面上的文字内容（`content.js`） | `content: 补齐学校与项目信息` |
| `fix` | 修 bug | `fix: 修复移动端导航展开后无法点击的问题` |
| `refactor` | 重构（对外表现不变） | `refactor: 拆分渲染函数…` |
| `chore` | 杂项（配置、脚本、依赖） | `chore: 导入 AI 生成的初版网站作为基线` |
| `chore(deploy)` | 部署相关 | `chore(deploy): 添加云服务器部署配置与一键部署脚本` |

书写要求：

- 一句话说明用**动词开头**（新增/改为/修复/删除/补充），不超过 50 字；
- 正文分条写"改了哪些文件、为什么改、有什么影响"，方便以后回看；
- 一次提交只做一件事——内容和样式混在一起，以后想回退样式就回退不干净。

## 二、分支策略

个人项目不引入复杂流程，采用**单主干 + 临时分支**：

```
main ──●──●──●──●──●──────────▶  始终可部署到服务器
             \        /
              ●──●──●          临时分支：feat/projects-page、fix/mobile-nav
```

| 规则 | 说明 |
| --- | --- |
| 主分支 | `main`，任何时刻都应该是"能直接部署"的状态 |
| 临时分支 | 大改动（如新增页面、换整体设计）先建分支，做完验证通过再合并回 `main` |
| 提交频率 | 每完成一个可验证的小步骤就提交，宁可多提交，不要攒一大坨 |
| 不提交什么 | `Thumbs.db`、`*.log`、打包产物（见 `.gitignore`） |
| 行尾处理 | `.gitattributes` 统一 LF（脚本要在 Ubuntu 上运行，CRLF 会让 shell 脚本报错） |

## 四、每次提交怎么做的（命令示例）

```bash
# 1. 看一眼改了什么
git status
git diff

# 2. 只把这次相关的文件加进来（不要无脑 git add -A）
git add assets/js/content.js

# 3. 提交，信息按规范写
git commit -m "content: 补齐学校名称与大一课程成绩"

# 4. 看提交历史，确认这条记录清楚
git log --oneline -5
```

大改动建议用编辑器写长信息：

```bash
git commit    # 不写 -m，会打开默认编辑器，第一行当标题，空一行写正文
```

## 五、常用命令速查

| 目的 | 命令 |
| --- | --- |
| 看历史（一行一条） | `git log --oneline` |
| 看历史（含时间与文件统计） | `git log --pretty=format:"%h %ad %s" --date=short --stat` |
| 看某次提交改了什么 | `git show 0d8f79f` |
| 看两个版本之间的差异 | `git diff 7a0e4d3 HEAD --stat` |
| 撤销某个文件的改动（未提交） | `git restore assets/js/content.js` |
| 撤销最后一次提交但保留改动 | `git reset --soft HEAD~1` |
| 临时存一下未完成的改动 | `git stash` / `git stash pop` |
| 给某个版本打标签（如上线） | `git tag -a v1.0 -m "首次部署上线"` |
| 查看当前所在分支 | `git branch -v` |
| 建临时分支改大功能 | `git switch -c feat/projects-page` |
| 合并回主干 | `git switch main` → `git merge --no-ff feat/projects-page` |

## 六、回退与恢复（改坏了怎么办）

```bash
# 场景 1：还没提交，改乱了 → 丢弃单个文件的改动
git restore index.html

# 场景 2：已经提交，但想回到上一个版本（保留改动在暂存区）
git reset --soft HEAD~1

# 场景 3：想彻底回到某个历史版本（危险，会丢改动，确认后再执行）
git reset --hard 7a0e4d3

# 场景 4：只是想看看旧版本长什么样 → 开一个临时目录检出，不动当前工作区
git worktree add ../old-version 7a0e4d3
```

## 七、和部署的关系

- `main` 分支的任何提交都应该是**可上线**的；
- 推荐节奏：改内容 → 本地验证 → `git commit` → 执行 `deploy\deploy.ps1` 上线 → 打一个 tag；
- 服务器上的版本与 Git 版本一一对应，出问题能靠 `git show` 精确定位"哪次改动引入了问题"；
- 部署脚本会在服务器上保留最近 5 份备份，回滚见 `docs/05` 的故障排查部分。
